# How the Excel Files Are Designed

## Overview

Three workbooks, sharing one data model ([`data-model/priorities.dbml`](../data-model/priorities.dbml)):

- **`management/preparation.xlsx`** — Management's Preparation-phase workbook. Holds
  the reference/master data: Centres, Position, ProblemSet, InitiativeType,
  AssistanceType, RatingLookup, Resources, and the master Priority list with full
  Tactical/Initiative/Assistance scoring.
- **`templates/centre-template.xlsx`** — the Centre Lead data-entry workbook. Embeds
  a read-only copy of every reference table from `preparation.xlsx`, plus the Centre
  Lead's own input tables: Teams, Priorities & Ranking, Resource Allocation.
- **`management/consolidation/consolidation.xlsx`** — Management's Consolidation workbook. Combines
  the six completed centre files (returned by Centre Leads) into consolidated views:
  which priorities each centre is working, how they're ranked, and how much
  resourcing (FTE) each priority is actually getting. See "Consolidation workbook"
  below.

All three workbooks are generated by Python scripts rather than hand-built, so the
design is reproducible and versioned alongside the data.

## Data model simplifications

The DBML file is the source of truth, but a few deliberate simplifications were made
where the draft schema was ambiguous or impractical in Excel:

1. **RatingLookup bands** — the six raw 0–5 inputs (Intent, Capability, Consequence,
   Dividend, Feasibility, Cost) are left as plain numbers; only the computed outcomes
   (Likelihood, Risk, Value) are banded and colour-coded, since those are what get
   reviewed.
2. **RiskBandLevel** is computed as `LikelihoodLevel` (the 1–5 band index of the raw
   Likelihood score) × `Consequence`, giving a 0–25 range — the draft's wording
   ("Likelihood × Consequence") was ambiguous between the raw 0–25 Likelihood and its
   banded 1–5 level.
3. **Actor** stores a Centre Code (FK to Centres) instead of the draft's fixed
   Ottawa/Gatineau/Toronto enum, so it works for all six centres.
4. **LikelihoodScore/LikelihoodLevel** — the draft defined both with the same
   meaning; only `LikelihoodLevel` is kept.
5. `Priority.Title` is used as the join key everywhere (matching the DBML's
   `(Title, Type)` composite index) rather than a surrogate ID — fine as long as
   titles stay unique, which the synthesized data enforces, but worth a surrogate
   `PriorityId` if this ever needs to be more robust.

## Validation, without VBA

The Centre Lead template deliberately avoids VBA — native Excel only. What that buys:

- **Dropdowns** (Data Validation lists) keep Team, Type, Priority, Resource, and
  Position entries consistent with the master lists, and constrain both Allocation %
  columns to 5% steps.
- **Dependent dropdown**: the Priority Title dropdown on 'Step 2' is filtered to the
  team's Priority Type automatically, via `=INDIRECT($C3)` resolving to a defined
  name literally named `Tactical`/`Initiative`/`Assistance` (see the gotcha below).
- **Custom-formula validation** blocks bad entries as they're typed: duplicate team
  names, duplicate rank within a team.
- **Live rollup + conditional formatting**: "Total %" columns recompute via
  `SUMIFS` and turn red/amber/green, so an over-100% team or person is visible even
  though nothing blocks the entry that caused it (see the trade-off note below).

**Known gap**: the duplicate-name/rank checks fire on manual entry, not on paste.
There's no way to close that gap without VBA (e.g. a `Worksheet_Change` handler) — a
deliberate trade-off, not an oversight.

**Trade-off, not a bug**: Allocation % on Steps 2 and 3 is a dropdown (5% steps), not
a custom-formula block — Excel's Data Validation only supports one rule type per
cell, so "must be from this list" and "must not push the total over 100%" can't
coexist in one native rule. The dropdown won, since a clean list of valid values
matters more day-to-day than a hard block; the Total % columns still flag an overage
visually, just not at typing time.

## Power Pivot Data Model

Both workbooks have their Tables wired into Excel's Data Model (Power Pivot), with
relationships matching the DBML's `Ref:` lines — e.g. `Resources.PositionTitle ->
Position.Title`, `Tactical.PriorityReference -> Priority.Title`, and (in the Centre
Lead workbook) `Priorities."Priority Title" -> Priority.Title`, linking a centre's
ranked priorities back to Management's master list.

**openpyxl cannot write this.** The Data Model is a proprietary embedded format
(`xl/model/item1.data`, an internal Analysis Services binary) that only Excel itself
can author. Wiring it requires driving a real, already-open Excel session over COM
automation (`pywin32`) — see `management/scripts/wire_data_model.py` and
`templates/scripts/wire_data_model.py`. The exact connection shape those scripts use
(`WORKSHEET;<path>` connection string, `CommandText="<file>!<table>"`,
`lCmdtype=7`/`xlCmdExcel`) is undocumented; it was reverse-engineered by doing
Excel's own "Add to Data Model" click once and reading back what connection it
created (`WorksheetDataConnection.Connection` / `.CommandText` / `.CommandType`).

**Known gotcha, cost real debugging time**: a Table's `displayName` and a workbook
**defined name** occupy the same namespace in Excel's object model — they can't be
identical. The Centre Lead template originally named its Tactical/Initiative/
Assistance reference tables the same as the dependent-dropdown defined names
(`Tactical`/`Initiative`/`Assistance`). Excel didn't error on open — it silently
**deleted the Table** on load, surfacing only as a generic "repaired records" log
naming the Table part, with no clue as to why. The fix: the reference tables are
named `TacticalScores`/`InitiativeScores`/`AssistanceScores`; the defined names keep
the plain names, since `INDIRECT()` needs them to match the Type column's text
exactly. If you add a new Table anywhere in either workbook, check its `displayName`
isn't also a defined name.

**Known limitation**: the Centre Lead template's `Priorities`/`ResourceAllocation`
tables can't relate to `Teams` until real team data exists — Power Pivot rejects a
relationship whose "one" side (`Teams."Team Name"`) contains *any* blank value.
Confirmed by testing directly (2026-08-17): shrinking the Teams table to a single
blank data row — the original theory being that Power Pivot's rejection was about
duplicate blanks specifically — still fails, with Excel's own error message
clarifying the real rule: no blank at all is allowed on a one-side key column,
whether or not it's duplicated. So there's no template-side workaround; re-run
`wire_data_model.py` (idempotent — skips what's already wired) once a Centre Lead
has filled in real teams.

## Structured references (`Table[Column]`) — two more gotchas

Beyond the Table/defined-name collision above, two more sharp edges turned up while
building the Centre Lead template's rollup formulas, both silent (no error dialog,
no repair log — the formula just quietly stops working):

1. **A column name containing an apostrophe breaks `Table[Column]` syntax.** A
   column was originally named `Allocation % of Person's Time`; any formula
   referencing `ResourceAllocation[Allocation % of Person's Time]` had that
   structured reference silently rewritten to `#REF!` by Excel on load — checkable
   via `Range.Formula`, not `Range.Value` (see below). No dialog, no log entry.
   Renamed the column to `Allocation % of Person Effort` and the problem vanished.
   Avoid apostrophes (and probably other punctuation) in any column name you intend
   to reference via `Table[Column]`.
2. **Data Validation custom formulas don't support structured references the way
   regular cell formulas do.** `COUNTIF(Teams[Team Name], $A2)` inside a cell
   formula works fine; the identical expression inside a Data Validation "custom"
   rule made Excel strip **all** Data Validation from that sheet on open ("Removed
   Feature: Data validation" in the repair log). The fix was mechanical: revert
   those specific rules to plain absolute ranges (`$A$2:$A$201`) — regular cell
   formulas elsewhere in the same workbook keep their structured references, since
   those aren't affected.

**If a formula error doesn't show up where you expect**: check `Range.Value` via
COM, not just whether the cell displays something. Excel returns error cells as a
raw negative integer through `Value` (not a `"#REF!"`-style string), which will
silently defeat a naive `isinstance(value, str)` check — this happened once already,
see `scripts/check_errors_excel.py`'s docstring. Read `Range.Text` (always a
string) or `Range.Formula` (to see what the reference actually resolved to)
instead.

## Process gap: static snapshot vs. live refresh

CLAUDE.md's Process section describes Management "ensuring the data is refreshed
(data connection to the preparation phase Excel file)" when cloning a centre file
from the template. **That's not what's built today.** `centre-template.xlsx`'s
reference sheets are a **static, point-in-time copy** of `preparation.xlsx`'s data,
baked in by `build_centre_template.py` at generation time — not a live, refreshable
Power Query connection to the Preparation workbook. If Management updates Priorities
or Resources after templates have already been cloned/distributed, those clones
won't see the change without being regenerated.

Building a real live-refresh connection (Power Query pointed at
`preparation.xlsx`, refreshed per-clone) is a reasonable next step, but wasn't done
here — flagging it rather than quietly leaving the gap undocumented. (The Power
Query technique now proven out for the Consolidation workbook below would make this
a lower-risk follow-on than it looked before that work.)

## Consolidation workbook

`management/consolidation/consolidation.xlsx` combines the six returned `centre-template.xlsx`
files into consolidated views. Built by
`management/consolidation/build_consolidation.py` (openpyxl — the shell: an
Instructions sheet with a source-folder config, and read-only copies of the
`Centres`/`Priority`/`Resources` reference tables the combined data relates to),
then wired up by two more scripts described below.

### Gathering the six files: Folder connector, not SharePoint Folder, not manual

Management points the workbook at one folder containing all six returned files
(the Instructions sheet's yellow `SourceFolder` cell) and Power Query's plain
**Folder** connector combines them. Two alternatives were deliberately rejected:

- **Manual copy/paste or one-file-at-a-time "Get Data from Workbook"** — not
  repeatable, no audit trail, breaks the moment a column shifts or a file's missed.
- **Power Query's "SharePoint Folder" connector** — targets the modern SharePoint
  REST surface Office 2021's Power Query expects; SharePoint 2013's classic
  experience has known compatibility friction with it, and it adds a live-auth
  dependency this project's "must work fully disconnected" constraint doesn't want.
  If the six files live in a SharePoint document library, that library is very
  likely also synced locally (OneDrive/SharePoint sync client) — point the plain
  Folder connector at that synced local path and get the same result with none of
  the risk.

### Why Team Name alone isn't a safe join key: the TeamKey composite key

Centres can name teams however they like (`CLAUDE.md`'s domain rules — "Centres can
create Teams as they wish"), and Team Name is only uniqueness-checked *within* one
centre's workbook. Two different centres can genuinely both have a team called
"Ops Team" — the dev fixtures below deliberately plant this collision. Each combine
query adds a `TeamKey` column (`CentreCode & "|" & [Team Name]`) before combining,
and every relationship involving Team Name is wired against `TeamKey` instead —
`|` was picked because it can't appear in a team name typed through the existing
dropdown/validation UI, so there's no ambiguity risk the way a hyphen or space
would have. `CentreCode`/`CentreName` come from each source file's own
`CentreCode`/`CentreName` defined names (see the Centre Name/Code fix above) — not
re-derived from a lookup, since a centre file has nothing to look its own code up
*against*.

### Authoring the Power Query combine queries: `wire_power_query.py`

The three combined tables (`Teams_All`, `Priorities_All`, `ResourceAllocation_All`)
are Power Query outputs, authored and wired by
`management/consolidation/wire_power_query.py` (COM, against an already-open
Excel). This turned out to be **fully scriptable** — no manual Excel UI step
needed — but only via a specific chain of COM calls worked out by direct
experimentation, because two more-obvious approaches don't work:

1. `Workbook.Queries.Add(Name, Formula)` authors the M query itself. Reliable,
   ordinary COM — works exactly as documented.
2. Loading that query straight into the Data Model via `Connections.Add2` with an
   OLEDB Mashup connection string (`Provider=Microsoft.Mashup.OleDb.1;Data
   Source=$Workbook$;Location=<query>`) **does work**, but Excel names the
   resulting Model table something generic like `Query`/`Query1` regardless of
   the query's real name or the connection's `Name` parameter — and
   `ModelTable.Name` has no setter, so there's no way to fix it afterward. Dead
   end for anything that needs to reference the table by name (every relationship
   and DAX measure here does).
3. The actual recipe: load the query onto a worksheet as a real Table first
   (`Worksheet.ListObjects.Add(SourceType:=0, Source:=<the same OLEDB Mashup
   connection string>, Destination:=...)`, then set `QueryTable.CommandType = 2`
   (`xlCmdSql`) and `QueryTable.CommandText = "SELECT * FROM [<query>]"` before
   `.Refresh()`) — the resulting `ListObject` **can** be renamed, unlike a
   `ModelTable`. Rename it to the real target name, then add *that* worksheet
   Table to the Data Model with the exact same `WORKSHEET;` connection recipe
   already proven throughout this codebase
   (`management/scripts/wire_data_model.py`, `templates/scripts/wire_data_model.py`)
   — which then correctly picks up the renamed name. This also means the combined
   data is visible on an ordinary worksheet (the `*_All (data)` sheets) for
   spot-checking, not hidden inside an opaque Model-only connection.

A real bug this caught: the first version of the combine query extracted the raw
`Priorities`/`ResourceAllocation` Tables as-is, pulling in all ~195 blank
pre-built template rows per file along with the real ones (600 rows combined from
3 tiny test files, instead of the expected 5). Fixed by filtering
`[Team Name] <> null and Text.Trim([Team Name]) <> ""` before combining — Team
Name is the first field filled on any real row (see
`docs/centre-lead-user-guide.md`), so a blank one reliably means "unused template
row," not "unusually empty real submission."

### Wiring the Data Model: `wire_data_model.py`

`management/consolidation/wire_data_model.py` adds the static reference tables
(`Centres`, `Priority`, `Resources`) via the same proven `WORKSHEET;` recipe, then
wires 5 relationships — the 3 combined tables to each other and to the reference
tables, via `TeamKey` where Team Name is involved:

```
Priorities_All.TeamKey            -> Teams_All.TeamKey
ResourceAllocation_All.TeamKey    -> Teams_All.TeamKey
Priorities_All.Priority Title     -> Priority.Title
ResourceAllocation_All.Resource   -> Resources.FullName
Teams_All.CentreCode              -> Centres.CentreCode
```

Unlike the blank-Teams-row problem that blocks 2 of `centre-template.xlsx`'s
relationships until real data exists, all 5 of these wired cleanly on the first
try against the dev fixtures — `TeamKey`/`Priority Title`/`Resource`/`CentreCode`
are always populated on a *combined* (i.e. already-submitted) row, so the
one-side-can't-be-blank rule Power Pivot enforces was never at risk here.

### DAX measures: `add_measures.py`

The first DAX measures anywhere in this project — no prior COM precedent to
follow (`wire_data_model.py` only ever touches tables/relationships). Gotcha:
`Model.ModelMeasures.Add`'s `FormatInformation` parameter looks optional but
passing `None` fails every time with a bare, useless "Exception occurred" — it
needs a real format object (`model.ModelFormatDecimalNumber`,
`model.ModelFormatWholeNumber`, etc.), not `None` and not an omitted argument.

- **`Total FTE := SUM(ResourceAllocation_All[Allocation % of Person Effort])`** —
  correct via ordinary relationship propagation when sliced by Team/Centre; no
  special handling needed.
- **`FTE Delivered to Priority`** — the genuinely tricky one. A resource's
  contribution to a specific Priority is a **two-hop** calculation (their %
  allocation to a Team, times that Team's % allocation to the Priority), and
  `ResourceAllocation_All`/`Priorities_All` are two *fact* tables hanging off the
  same `Teams_All` dimension — not directly related to each other. DAX's default
  relationship propagation only flows dimension → fact, not fact → dimension →
  fact, so ambient filter context alone won't produce the right number; the
  measure has to explicitly correlate the two fact tables per `TeamKey`:
  ```dax
  FTE Delivered to Priority :=
  SUMX(
      Priorities_All,
      VAR CurrentTeamKey = Priorities_All[TeamKey]
      VAR CurrentAllocToPriority = Priorities_All[Allocation % of Team Effort]
      VAR TeamFTE =
          CALCULATE(
              SUM(ResourceAllocation_All[Allocation % of Person Effort]),
              FILTER(ALL(ResourceAllocation_All), ResourceAllocation_All[TeamKey] = CurrentTeamKey)
          )
      RETURN CurrentAllocToPriority * TeamFTE
  )
  ```
  `ALL(ResourceAllocation_All)` deliberately strips any pre-existing filter context
  on that table before `FILTER` re-applies exactly one condition (an exact
  `TeamKey` match) — the measure doesn't lean on relationship cross-filtering at
  all, so it's correct regardless of what's sliced in a PivotTable. Verified
  against all 5 Team/Priority combinations in the dev fixtures via `CUBEVALUE`
  (`=CUBEVALUE("ThisWorkbookDataModel","[Measures].[FTE Delivered to Priority]","[Priority].[Title].&[<title>]")`)
  — exact match on every one, including the two different centres' same-named
  "Ops Team" never cross-contaminating each other's FTE.
- **`Priority Rank (Min) := MIN(Priorities_All[Rank])`** — Rank is inherently
  per-team; don't read a min/avg across centres as meaning more than "the best
  rank anyone gave it." The `Priorities_All (data)` worksheet (Team/Priority/Rank/
  Resourced/Centre, one row per submission) is the real "Rankings" view — sortable
  and filterable as-is, not something that needs a separate aggregated number.

`CUBEVALUE` cell formulas (as used for verification above) are also the easiest
way to spot-check any Data-Model measure by hand later without needing a
PivotTable at all.

### The 3 "basic views": manual PivotTable creation, not COM

This project already has one **unresolved** COM failure creating a PivotTable off
a Data-Model connection (`PivotCaches().Create(xlExternal, wb.Connections("ThisWorkbookDataModel"))`
→ "Reference isn't valid" — see the PARKED item in `CLAUDE.md`'s Status section).
Retried once more here, against this real, fully-wired workbook, in case having
actual data changed anything — same failure, same generic error. Not a
parameter-tuning problem; treat it as a genuinely broken COM path in this Excel
version and don't sink more effort into it.

Since this is a **Management-only** workbook, a one-time manual setup step doesn't
touch Centre Lead simplicity at all. Create these once via Insert → PivotTable →
"Use this workbook's Data Model":

1. **Consolidated Priorities** — Rows = `Priority[Title]`, Columns =
   `Centres[Centre]`, Values = Count of `Priorities_All` rows (or filter to
   `Resourced = "Yes"`).
2. **Sum of FTEs by Centre/Team** — Rows = `Centres[Centre]` → `Teams_All[Team Name]`,
   Values = `[Total FTE]`.
3. **Sum of FTEs by Priority** — Rows = `Priority[Title]`, Values =
   `[FTE Delivered to Priority]`. Kept as a separate PivotTable from #2 rather than
   combined — the two measures are at different grains, and cramming both into one
   Pivot's Rows produces misleading subtotals.

For "Rankings," just widen/sort the `Priorities_All (data)` worksheet itself — no
PivotTable needed (see the `Priority Rank (Min)` note above).

Once created, tick **PivotTable Options → Data → "Refresh data when opening the
file"** on each (the UI equivalent of `PivotCache.RefreshOnFileOpen` — no COM
needed) so they stay current without a manual refresh click every time.

### Dev fixtures

No real completed centre submissions exist yet, so
`management/scripts/dev_fixtures/make_test_centres.py` generates 3 small,
hand-checkable ones (reusing `build_centre_template.main()` and `read_table()` —

It deliberately gives both `ECO` and `INF` a team called "Ops Team" to exercise
the `TeamKey` collision case. Expected values are documented in the script's

## Regenerating a workbook

```bash
# Preparation workbook
python management/scripts/build_preparation.py management/preparation.xlsx

# Centre Lead template (reads reference data out of preparation.xlsx)
python templates/scripts/build_centre_template.py management/preparation.xlsx templates/centre-template.xlsx

# One real, stamped centre file (centre-code must match a row in preparation.xlsx's Centres table)
python templates/scripts/build_centre_template.py management/preparation.xlsx out/Centre-CYB.xlsx CYB

# All six centres in one run, named Centre-<CentreCode>.xlsx
python templates/scripts/build_centre_template.py management/preparation.xlsx --all out/

# Consolidation workbook shell (default-source-folder is just a starting value
# for the Instructions sheet's yellow cell, editable afterward in Excel)
python management/consolidation/build_consolidation.py management/preparation.xlsx management/consolidation/consolidation.xlsx <default-source-folder>

# Dev fixtures — 3 small, hand-checkable "completed" centre files for testing
# the Consolidation workbook against (gitignored output, not shipped)
python management/scripts/dev_fixtures/make_test_centres.py management/preparation.xlsx
```

**Centre identity**: the Instructions sheet's Centre Name/Code cells are stamped
and locked at generation time from the `centre-code` argument (validated against
`Centres`), not left as an editable placeholder for the Centre Lead to fill in —
closes a real gap where those cells previously defaulted to hardcoded
`"Example Centre"`/`"EX"` values with nothing to keep them in sync with the
filename. Two defined names, `CentreName`/`CentreCode`, expose the stamped
values by name (not a hardcoded cell address) for anything — e.g. the
Consolidation workbook's Power Query — that needs to read them back.

Then, with the output file open in Excel:

```bash
python management/scripts/wire_data_model.py preparation.xlsx
python templates/scripts/wire_data_model.py centre-template.xlsx

# Consolidation workbook — run in this order, same open-in-Excel-first pattern
python management/consolidation/wire_power_query.py consolidation.xlsx
python management/consolidation/wire_data_model.py consolidation.xlsx
python management/consolidation/add_measures.py consolidation.xlsx
```

Then, manually, once: create the 3 PivotTables described in "Consolidation
workbook" above via Insert → PivotTable → "Use this workbook's Data Model" — see
that section for exact field-well contents and why this one step stays manual.

**Formula verification, if you touch the formulas**: use
`scripts/check_errors_excel.py` (with the file open in Excel) — it scans every cell
of every sheet for error values via real Excel over COM, and is the check that
actually caught the two structured-reference bugs above. Treat
`scripts/recalc_windows.py` (LibreOffice, headless) as a syntax smoke-test only: it
has reported a workbook fully error-free three separate times when real Excel either
repaired it on open or silently replaced a working formula with `#REF!`. If you do
use it, point it at a **disposable copy**, never the file you intend to ship —
LibreOffice's `store()` rewrites the whole file, and its OOXML export has its own
conformance gaps.

**Python only runs on the home machine** (Microsoft 365) — it isn't available at
work (Office Professional Plus). Regenerate/rewire there, then carry the finished
`.xlsx` over.

## Tools used

- **Python 3.13** + [**openpyxl**](https://openpyxl.readthedocs.io/en/stable/) —
  builds workbook structure, formulas, Tables, Data Validation, and conditional
  formatting.
- **pywin32** (`win32com.client`) — drives a real Excel session over COM to wire
  the Power Pivot Data Model, author Power Query M queries, and add DAX measures
  (none of which openpyxl can touch), and to verify formulas actually compute
  correctly in Excel itself (`scripts/check_errors_excel.py`).
- **Power Query** (M) — combines the six centre files in the Consolidation
  workbook; authored via COM (`management/consolidation/wire_power_query.py`) per
  the recipe in "Consolidation workbook" above, not hand-typed in the UI.
- **DAX** (Data Analysis Expressions) — the Consolidation workbook's measures
  (`management/consolidation/add_measures.py`); see "Consolidation workbook"
  above for the two-hop `FTE Delivered to Priority` reasoning.
- **LibreOffice** (headless, via `scripts/recalc_windows.py`) — formula-syntax
  smoke test only, on disposable copies; not trusted as a proxy for "opens cleanly
  in Excel" (see the structured-reference gotchas above).
- **[DBML](https://dbml.dbdiagram.io/docs/)** — the schema notation used in
  `data-model/priorities.dbml`.

For Power Pivot / Data Model relationships and DAX beyond what's described above,
search Microsoft Learn or Microsoft Support for "Excel Data Model relationships" and
"DAX basics" — official article URLs move around too often to link reliably here.
